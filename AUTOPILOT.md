# Yo — автономное производство

## Графическая серия: дополнение от 27 октября 2026

Текущая планка: [Microsoft V3](docs/motion-series-standard-2026-10-27.md). Перед новым графическим выпуском прочитать её один раз вместе с [моушн-регламентом](docs/motion-production-playbook.md). Эти уточнения имеют приоритет для серии: разработанная SVG/2D-графика без фотографий и сгенерированных растровых сцен допустима как итоговый язык, обязательного 3D нет. С первого монтажа нужны выразительная речь, крупные смысловые действия, развитие сцены по репликам, читаемые акценты со свечением и точные контакты. Нижние субтитры остаются дословными и одноцветными; повторяющийся нижний таймлайн не возвращать. Тире в озвучке запрещены. Принятый фильм заморожен; документация не разрешает его пересборку.

20 октября 2026: внедрено ревью Astra; автономность разрешена пользователем ранее. `Yo` (также `yo`, `YO`, `Йоу`, `Йо`) в новом чате этого проекта запускает ОДИН новый выпуск целиком. `Yo, 75 секунд` меняет длину видео; `Yo, 60 секунд, к 18:00` добавляет дедлайн в часовом поясе пользователя. Иное явное задание выше умолчаний. Просто приветствие Yo вне этого проекта не запускает производство. Создание этой команды не является её первым запуском.

## Параметры обычными словами

`Yo, уклон: отношения, провокационно` — выбрать тему внутри уклона. `Йоу, актуальное, 60 секунд` — найти свежую тему и проверить факты/даты. `Yo, что если Белла выбрала Джейкоба и не заинтересовалась Эдвардом, 75 секунд` — завязка уже задана: сделать собственную альтернативную ветку, а не выбирать другую тему. Это примеры синтаксиса, не команды на выпуск сейчас.

Разобрать отдельно длительность видео, дедлайн, уклон, тон, жанр и явную завязку. Сохранить их в brief и production.json. Нет уклона — самостоятельный выбор объясняющей темы. Пикантность/провокация не заменяет сюжет и не разрешает выдумывать научные/новостные факты. Не менять обязательный голос из-за жанра.

## Старт без лишнего контекста

Правила экономии контекста, ранней проверки субтитров и повторного использования технической основы — в разделе «Экономия без снижения качества» ниже; применять при каждом новом выпуске.

1. Прочитать PROJECT.md один раз и выполнить `python3 tools/production/yo.py context` плюс `preflight`. Не открывать архивы, старые логи, node_modules, весь STUDY и все навыки.
2. Через актуальные инструменты обнаружить ElevenLabs и сделать подходящую read-only проверку доступа/голоса. Проверить ресурсы для выбранной техники. Снимок доступности в старом review не действителен для нового запуска. Платную пробу не выдавать за бесплатную проверку подключения. При необходимости ключей/логина сообщить ровно блокер; не заменять голос молча.
3. Первым коротким обновлением сообщить: длительность видео, автономный выбор темы/стиля, предварительный диапазон времени до результата и ограничение точности. После короткого теста/измерения речи уточнить ETA. Час — пример пользователя, а не обещание фиксированного SLA. Если есть дедлайн, проверить реалистичность сразу; не скрывать прогноз опоздания.

## Внутренние решения вместо вопросов

4. Если пользователь задал конкретную завязку, сохранить её и разработать последствия; тему повторно не выбирать. Иначе выбрать 3–5 новых кандидатов внутри заданного уклона (без уклона — объясняющий формат) по знакомому предмету/ставке, неожиданности, механизму и силе ответа; проверить смысловые повторы по контексту и actual briefs. Для объяснения/актуального собрать минимально достаточные первичные/профильные источники; для альтернативной истории — проверить нужный канон/контекст, явно отделить допущение и выстроить внутренне логичные последствия. Выбрать одну самостоятельно, краткое основание в `brief.md`. Нельзя обещать максимум виральности или копировать неподтверждённый хайп.
5. Создать новую папку: `python3 tools/production/yo.py init --slug <slug> --topic-key <key> --topic '<название>' --duration <секунды> [--direction <уклон/тон>] [--genre explainer|current|counterfactual|fiction] [--premise <завязка>] [--deadline <дата-время-зона>]`. Команда резервирует ключ; будущие запуски видят его. Для продолжения существующего задания использовать его production.json, не создавать новую тему. CLI защищает точный ключ, смысл и aliases проверяет агент.
6. Одна brief-карточка по STYLE_BRIEF_TEMPLATE.md. Пройти EDITORIAL_STANDARD.md: выбрать способ рассказа, проверить обещание хука, промежуточные открытия и развязку. До основного TTS закрепить связку «обещание → показанный результат → последняя реплика + последнее действие» по EDITORIAL_STANDARD.md, п. 5; красивое противопоставление без ответа зрителю не считать готовой концовкой. Ведущий проходит роли продюсера, режиссёра, моушн-дизайнера/разработчика, редактора/фактчекера и звукового дизайнера по MOTION_DIRECTION.md; осмысленная делегация разрешена. Свести решения в общую brief, без копий отчётов на роли.
7. Самостоятельно выбрать цельный стиль по MOTION_DIRECTION.md: полноэкранный мир, настоящий центр, сочная материальность, смелая речь, числа как действия и смысловые переходы/фоли. До основного TTS записать поведение важных величин (источник, единица, финал, удержание), камеры и рискованных взаимодействий; не оставлять это на косметику после озвучки. Внутренняя рекомендация/рандомайзер не требует апрува в Yo. Отличие постановки проверить по пространству, материалу, камере, действию и ритму; каталог приёмов при необходимости — VISUAL_DEVELOPMENT.md, подробное наблюдение — один нужный раздел STUDY. Не читать все референсы. Применить motion-story-director; технический навык только для выбранной техники. Делегировать конкретную режиссёрскую/моушн-задачу по MOTION_DIRECTION.md, не создавать агентов формально на каждую редакционную роль.

## Производство и восстановление

Перед этапом 8 применить условия художественного отказа из MOTION_DIRECTION.md («Разбор провала “Мышцы без отдыха”»): форма/силуэт, действие всего нужного тела, связанная вторичная анимация, материал и второй тип сцены. Дешёвая реализуемость и исправный контакт сами по себе не допускают основную озвучку/полную сборку.

8. До основного TTS отредактировать всю связку тема → хук → голос → первое действие → оформление. Допуск ведёт продюсер: оценить целостность речи, режиссуры и моушна; тест должен показывать реальный уровень энергии и изменения, не титульную карточку. Проверить аниматик и реальный начальный фрагмент 3–8 секунд с выбранной речью. Самое сложное более позднее действие проверять отдельно коротким тестом, если начальный тест его не покрывает. Не принимать начало из-за хорошей сцены дальше по таймлайну. Этот допуск пройти до полного набора ассетов и полной сборки. Тест должен содержать действие, текст и переход. Озвучка, событие и смысл совпадают с первых секунд, каждый элемент связки достаточно силён. Не генерировать полные альтернативные версии ради выбора оформления.
9. Перед каждым платным вызовом сохранить полные смысловые параметры в JSON и выполнить `generation-reserve` по tools/production/README.md. Только ответ `submit_once` разрешает один вызов MCP; `inspect_existing` означает проверку уже начатой задачи, `reuse` — готовый файл. Немедленно сохранить provider ID через `generation-update`, после скачивания — хеш результата. Не обходить журнал новой пунктуацией/фиктивным параметром. Неизвестный исход после таймаута не является отказом провайдера; повтор лишь после подтверждённого отказа, evidence и явного `generation-retry`. Журнал не перехватывает прямые MCP-вызовы: обязательный маршрут соблюдает исполнитель. В генеративных инструментах явно задавать `generations_count=1`: умолчание коннектора может быть четыре. Для длинного запроса сначала estimate_only, сохранять ID/цену; разрешение Yo на нужные генерации уже дано, повторный апрув на обычный этап не нужен. Не публиковать signed URL и полные большие ответы: результат на диск, в контекст компактный статус/путь. Основная речь Nikolay → фактические тайминги → сцены и дословные сабы → действия/фоли/микс. Планировать длину заранее, не обрезать ответ и не маскировать неподходящий темп. Сохранить источник/параметры/файл каждого генеративного запроса, перед повтором проверить уже начатую задачу. Обычно одна основная речь и один полный экспорт; это экономный ориентир, а не запрет исправлять дефекты.
10. До сборки создать единый timeline.json (кадры сцен, именованные события с локальными смещениями); проверить `yo.py timeline`. Сцены, фоли, переходы и фон получают времена из него; tools/production/scene-clock.cjs даёт одно время адаптерам. Геометрия/действие сцены — общий компонент с явным временем, без отдельной копии тела сцены для файлового рендера. При выборе альтернативного экспорта сначала короткая проверка кириллицы/теней/состояний; при пригодности титры композить в том же проходе кодирования. Старые обходы не удалять вслепую. Перед тяжёлым процессом уведомить, выбрать лёгкую пригодную технику, один процесс. Кэш кадров только по содержимому всех входов: `cache-key <источники> <тайминги> <ассеты/шрифты> --settings '<renderer/version/fps/size/seed>'`; каталог `cache/<render_key>/` отдельно от входов; обход не читает cache/renders/reviews/node_modules. Не передавать всю папку выпуска со служебными JSON как вход: перечислить реальные исходники/ассеты/таймлайн. Одного существования `00001.png` недостаточно. Не переносить жёстко заданные 60с/1800 кадров/прошлые сцены в новую историю.
11. После дефекта править причину и короткий участок со стыками, затем финальный файл и требуемые проверки. После двух неудачных адресных попыток пересмотреть метод/приём, не повторять вслепую. Не прекращать разрешённую работу ради формального лимита итераций; при реальном внешнем блокере сообщить его, сохранить точку продолжения. Файл с известным дефектом не называть готовым.

## Экономия без снижения качества

Решение пользователя от 20 октября 2026. Экономить на повторной работе и объёме контекста; сохранять фактчек, разработку сценария/концовки, реальную пробу начала, проверку сложного действия и полный тихий просмотр финала. Модель автоматически не понижать. Уже принятые фильмы и их источники ради этих правил не менять.

- **Один новый выпуск — один свежий чат.** Рекомендовать запуск следующего выпуска в новом чате этого проекта с `Yo` и нужными параметрами. Самостоятельно чаты не создавать. Если пользователь продолжает текущий незавершённый выпуск, использовать его папку, brief, production.json, журнал и точку продолжения; новый чат не является поводом повторять генерации или начинать фильм заново. При переносе достаточно пути к выпуску, актуального состояния и следующего шага, без всей переписки.
- **Повторно использовать техническую основу.** Брать существующие helpers таймлайна/scene-clock, журнал генераций, проверенный способ субтитров, микширования, экспорта и полноэкранную центрированную основу без прежней шапки/контейнера. Переносить только подходящую техническую часть, проверяя зависимости и реальные входы; прошлый проект целиком не является универсальным шаблоном. Тема, постановка, предметные действия и визуальный характер разрабатываются для новой истории. Не извлекать библиотеку и не мигрировать закрытый фильм ради самого переиспользования.
- **Короткие ответы инструментов.** Читать один раз нужный документ и затем конкретный раздел; искать только необходимые инструменты/поля схемы. Полные ответы, расшифровки и журналы сохранять на диск, в контекст выводить статус, ID задачи, путь результата, нужные метрики или ошибку. Не печатать весь каталог инструментов, signed URL, base64 и полные ASR words. Повторно читать только изменённое или нужное для конкретной ошибки.
- **Ожидать процесс вместо частого опроса.** Использовать ожидание завершения/обновления статуса, соблюдать интервал провайдера; если его нет, начинать с 20–30 секунд и увеличивать интервал при неизменном состоянии. Не запускать заново задачу из-за долгого ожидания. Ожидания не блокируют общение более чем на 60 секунд; содержательные обновления пользователю сохраняются. Сам локальный рендер не расходует токены модели; частые обращения и анализ вокруг него расходуют.
- **Субтитры проверить до полного экспорта.** После фактических таймингов речи проверить последовательное покрытие читательского текста, пустые элементы, пересечения/выход за длительность и максимум две строки через существующую `check_captions` в tools/production/yo.py. Отдельно проверить покадровые границы по реальному условию показа renderer: выявить исчезновения на 1–3 кадра между соседними фразами; случайные разрывы убрать, осмысленные паузы сохранить. Собрать фразы по смыслу, не оставлять случайное последнее слово отдельной карточкой. Измерить строки выбранным шрифтом в принятом блоке, проверить переносы/переполнение на лёгком текстовом проходе или коротком фрагменте. `check_captions` сама не проверяет смысловое деление, ширину строк и микропровалы; не приписывать ей эти возможности. Это ранняя проверка, а не новый дорогой полный просмотр.
- **Исправления проверять адресно.** Сначала участок с дефектом и стыками, затем нужный экспорт. Один полный тихий просмотр окончательного видеопотока обязателен. Не пересматривать идентичный уже проверенный видеопоток только из-за новой упаковки или изменения аудио; идентичность подтвердить хешем видеопотока, обновить технические проверки/квитанцию финальных файлов. Изменение картинки или таймингов требует просмотра нового финального видео. Не снимать допуск по контрасту, движению или фактам ради экономии.
- **Эффект измерять без выдуманных процентов.** На следующем выпуске сохранить доступные снимки общего пятичасового лимита в начале/конце и на границах основных этапов, вместе со временем и названием этапа; без опроса после каждого инструмента. Если данные недоступны, отметить это. Разница — расход общего аккаунта за интервал, с округлением и возможным вкладом других чатов; не выдавать её за точный расход этого выпуска. Токены из журнала и процент лимита учитывать отдельно, универсальной формулы пересчёта нет. Не обещать заранее процент экономии и не запускать отдельный подробный аудит без необходимости.

## Допуск к выдаче

12. Повторно проверить связку темы/хука/голоса/первой анимации/оформления в финальном файле и записать opening evidence. Для вымысла facts evidence описывает канон/допущение/внутреннюю логику, а не выдаёт историю за научный факт. Мастер нужной длительности; тихую копию создать `yo.py make-silent <master> <new-output>`, без перекодирования видеопотока. verify отклоняет отличающееся видео; просмотреть весь финал в движении тихо. Проверить рябь/мерцание/исчезновения, все текстовые границы, контраст каждой подписи/выноски на реальном движущемся фоне и полноэкранную композицию по LAYOUT_STANDARD.md, числовые события/переходы/завершённость действия по MOTION_DIRECTION.md; платформенных резервов и Safe Zone-проходов нет; звук — технически по файлу, уровням и таймингу микса. Не выводить художественный pass из ffprobe/контактного листа. По решению пользователя от 20.10.2026 акустическое ревью и перепроверка ударений не требуются и не блокируют выпуск. Не заявлять, что они выполнены; pronunciation исключён из обязательных gates.
13. В production.json указать относительные `artifacts`: master, silent, captions, reader, source_dir; `render_inputs` (исходники, тайминги, шрифты/ассеты) и `render_settings`. Новые production.json содержат timeline_file: указать этот файл явно в render_inputs; длительность/fps таймлайна должны совпасть с целью. В review.json: `artifact_hashes` для master/silent/captions/reader, `render_key`, `checks` с facts, opening, motion_full, text_boundaries, flicker, audio. Геометрия берётся из текущего полноэкранного production/layout-1080x1920.json; нижняя позиция сабов в нём — стартовая рекомендация, не контейнер сцены. Safe Zone и gate phone_safe_areas отменены. Для audio — технические измерения/тайминги; pronunciation не требуется. У каждого status pass только после фактической проверки и evidence — путь к непустому файлу с методом/результатом/пределами. Можно один review.md для нескольких проверок. Запустить `python3 tools/production/yo.py verify <episode>`. Этот CLI не заменяет проверки, лишь проверяет формат/совпадение файлов и наличие записей. Если запись не отражает реальную проверку, pass запрещён.
14. После всех проверок записать state ready и обновить краткий topic-history/style-паспорт; оставить источники/ассеты/тайминги. Главной ссылкой выдавать мастер с аудио; тихую копию не открывать пользователю автоматически как основной результат. Дать пользователю ссылку на MP4 и проект, фактическую длину и коротко результат/существенные пределы. Не публиковать и не считать собственную выдачу пользовательским апрувом для обложки.

Работа продолжается в активной задаче, пока пользователь отсутствует. Не обещать работу при закрытом приложении, недоступном исполнителе или исчерпанном лимите; не создавать расписания/фоновые задачи без запроса. При возобновлении читать одну карточку и состояние, переиспользовать проверенные ассеты, не начинать всё заново.

Конкретный путь ElevenLabs после переподключения: creative_list_voices (проверить точный voice_id) → creative_get_model_schema для eleven_multilingual_v2; для фоли — sfx/eleven_text_to_sound_v2.
